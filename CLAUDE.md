## What it is

A **Windows Forms system-tray utility** that rebuilds the custom taskbar toolbars Windows 11
removed: point it at folder(s), and it shows their files/shortcuts as a cascading tray menu,
launching them on click. Global hotkey, per-folder icons, dark-mode, 10 languages, portable
(no installer), self-updating from GitHub releases.

- `Program.cs` — entry point, single-instance mutex, update hand-off, launch.
- `SettingsForm.*.cs` — the tray host and settings UI (split across partials).
- `Services/` — `ConfigurationStore`, `FolderScanner`, `GitHubReleaseClient`, update installer.
- `Extensions/` — `HotKeys`, shell icons/context menu, theming, message filters.
- `Models/` — configuration + release/update DTOs.
- Native interop is **source-generated by CsWin32** from `NativeMethods.txt` — add the API
  name there rather than hand-writing a `DllImport`.

## Analyzer / style reality

- **.NET 8** (`net8.0-windows`), WinForms, `Nullable=enable`, `ImplicitUsings=enable`.
  `RollForward=LatestPatch`. **Not .NET 10** — do not "modernize" the TFM.
- **No `TreatWarningsAsErrors`, no `Directory.Build.props`, no StyleCop.** The build is at
  **0 warnings today** — that plus `dotnet format` is the whole style gate. Keep both green.
- **`.editorconfig` trap:** it lives at **`src/TrayToolbar/.editorconfig`** with `root = true`
  — so it applies to the **app project only**. `src/TrayToolbar.Tests/` is **not** covered by
  it. Do not assume one style config spans the solution.
- **Platforms are `x64;ARM64`.** The test project declares **no `AnyCPU`**; a solution build
  resolves to `x64`. CI passes `-p:Platform=x64` explicitly.
- Tests are **MSTest** (not xUnit).

## Real traps (each verified in the code)

- **A crash during startup is completely silent.** `Program.Main` runs `ProcessUpdate()`,
  `EnsureSingleInstance()`, `SetShowInTray()`, `MigrateConfiguration()`, and `HotKeys.Enable()`
  **outside** its `try/catch`. Only the `Application.Run` loop is wrapped, and the sole
  diagnostic is an `Error-<timestamp>.txt` written by that catch. Fail earlier and there is
  **no file, no console, no tray icon** — the app simply never appears. See the logging doc.
- **12 silent `catch { }` blocks** across the app (`ConfigHelper`, `ConfigurationStore`,
  `SystemTheme`, `UpdateHelper`, `FolderScanner`, …). Failures here are invisible by
  construction. Do not add a 13th.
- **`HotKeys.Register` ignores the `RegisterHotKey` return value** and adds the id to
  `RegisteredHotKeys` regardless — the app believes it owns a hotkey it may not have got.
- **`ConfigurationStore.WriteConfiguration` deletes the config file, then writes it.** Not
  atomic. It is the user's folders, filters, and hotkeys.
- **`FolderScanner.EnumerateFilesCore` recursion is unbounded** — no depth cap, no visited
  set. A directory junction loop under a scanned folder recurses forever. See the logging doc.
- **The update path replaces the running executable and relaunches it** (`UpdateHelper`:
  download → verify → `File.Copy` over the exe → `Process.Start`). Read
  `docs/update-security.md` before touching it; it is a trust boundary, not just IO.
